# Decisiones de diseño

Formato: fecha, decisión, porqué.

## Heredadas de las reglas de negocio
- DT-001: la lógica de negocio vive en el backend.
- DT-002: SQL directo, delegando procesamiento a la base cuando corresponda, sin depender por completo del ORM.
- DT-003: toda consulta SQL directa es parametrizada.
- DT-004: los datos de tarjeta los guarda la pasarela de pago.
- RN-003: ingreso con Google en primera instancia.

## Estrategia de pruebas
- DT-005 (2026-10-07): el almacenamiento correcto de datos se valida con tests de integración por módulo de dominio contra una base Postgres de prueba (local o rama de Neon), consultando con SQL. Porqué: son rápidos y exactos, y es la única forma de probar de verdad el SQL directo (DT-002, DT-003); un test de navegador solo ve el dato de forma indirecta. No se usan mocks de la base.
- DT-006 (2026-10-07): Playwright se incorpora recién cuando exista el flujo de compra, y se limita a 3 a 5 tests de humo de caminos críticos (ingreso, ver dieta, armar carrito, hacer pedido). Porqué: los tests de punta a punta son lentos y frágiles; si se prueba todo, el mantenimiento supera el beneficio. Costos a resolver antes: base de prueba con datos controlados, ingreso con Google simulado (Google real bloquea bots, RN-003), pasarela en modo de prueba, y navegadores en CI. Hoy no se instala.

## Proyecto base
- DT-007 (2026-10-07): Next.js 16 con App Router, TypeScript, Tailwind 4, ESLint, carpeta `src/`, alias `@/*`, npm. Porqué: App Router es la arquitectura vigente; `src/` deja la raíz para configuración y documentación (`docs/`, `.claude/`); ESLint es el linter más documentado y el que asume shadcn/ui; npm ya está instalado y es lo más simple. Se descartaron por ahora React Compiler, Cache Components y Rspack: agregan complejidad sin una necesidad concreta todavía. **Corrección (2026-10-08, DT-031):** el instalador de Next 16.4 dejó `cacheComponents: true` y `partialPrefetching: true` en `next.config.ts` aunque no se pidió; Cache Components está activo desde el commit inicial.
- DT-008 (2026-10-07): shadcn/ui inicializado con la configuración por defecto (estilo `base-nova`, color neutral, íconos lucide). Cada componente se agrega cuando se necesita.
- DT-009 (2026-10-07): script `typecheck` = `next typegen && tsc --noEmit`. Porqué: Next genera tipos globales (por ejemplo `LayoutProps`) durante el build; sin generarlos antes, `tsc` falla en un árbol limpio.
- Nota (2026-10-07): `npm audit` informa 9 vulnerabilidades altas con una única causa: `braces` (DoS por patrones anidados), arrastrada por `fast-glob` en `eslint-config-next` y en el paquete `shadcn`. Es código de herramientas (lint y CLI de shadcn), no del sitio en ejecución; ojo que `shadcn` figura en `dependencies`, por eso `npm audit --omit=dev` también lo marca. Supabase no agrega ninguna. No se aplica `npm audit fix --force`: bajaría `eslint-config-next` a la 14 y `shadcn` a la 1.0. Revisar cuando salgan versiones corregidas.
- Nota (2026-10-07): Node local es 20.17.0 y la CLI de shadcn pide >= 20.18.1. Funcionó con advertencia; conviene actualizar Node.

## Base de datos y autenticación
- DT-010 (2026-10-07): se usa Supabase (PostgreSQL + autenticación) en lugar de Neon. Porqué: trae el ingreso con Google (RN-003) integrado, lo que evita sumar y mantener una librería de auth aparte; sigue siendo PostgreSQL estándar, así que el SQL directo parametrizado (DT-002, DT-003) funciona igual; y es más reconocido en el mercado, lo que suma para mostrar el proyecto. Contrapartida: más acoplamiento al proveedor; para mitigarlo, el acceso a datos queda dentro de los módulos de dominio y no en la UI. Paquetes instalados: `@supabase/supabase-js` y `@supabase/ssr` (sesión con cookies en el servidor, necesario con App Router). Falta crear el proyecto en supabase.com y configurar variables de entorno.

## Estructura y pruebas
- DT-011 (2026-10-07): la lógica de negocio vive en `src/modules/<dominio>/` (`catalogo`, `dietas`, `pedidos`, `busquedas`, `usuarios`), separado de `src/lib/` donde shadcn deja `utils.ts`. Cada módulo se crea cuando llega su primera regla real, no antes: Git no versiona carpetas vacías y crear esquemas sin reglas definidas sería abstraer "por si acaso". Hoy casi todo lo que iría dentro está **[A DEFINIR]** (ver preguntas 1, 9, 10 y 11 de las reglas).
- DT-012 (2026-10-07): Vitest como runner de tests (`npm test`) y Zod para validar en el borde. La configuración es `vitest.config.mts` (no `.ts`): con Node 20.17 la versión `.ts` falla con `ERR_REQUIRE_ESM`. Hay un test de humo en `src/tests/humo.test.ts` que se borra cuando exista el primer test real.
- DT-013 (2026-10-07): `.env.example` versionado con los nombres de las variables de Supabase y sin valores; `.env.local` queda ignorado. La clave `SUPABASE_SERVICE_ROLE_KEY` es solo de servidor y nunca lleva prefijo `NEXT_PUBLIC_`. El `.gitignore` ignora `.env*` con la excepción `!.env.example`.

## Definiciones de negocio (resueltas en sesión 2026-10-07)
- DT-014 (2026-10-07, corregida por DT-019): roles únicos con permisos. Nutricionista: se registra con Google, postula vía formulario en perfil, admin/auditor aprueba/rechaza, recibe notificación. Mientras está pendiente actúa como Cliente. Perfil público: nombre, foto, dirección, teléfono. Privado: matrícula (no se valida al dar de alta). Auditor es un usuario elegido por el Administrador. Proveedor también requiere aprobación.
- DT-015 (2026-10-07): esquemas de Zod para dieta y producto en `src/modules/dietas/schema.ts` y `src/modules/catalogo/schema.ts`. Dieta: nombre, descripción, alimentos con cantidad/unidad/patrón, duración (días o indefinida), notas. Patrón de consumo: "X veces/semana" o "cada N días" (N<10, se repite). Producto: nombre, descripción, precio, marca, peso, volumen, imagen, stock, tipos de mascota, tipos de dieta, tabla nutricional (opcional). Tests unitarios de validación en `*.test.ts`.
- DT-016 (2026-10-07): negocio: solo venta de comida, no servicios de nutrición. Dietas no tienen costo en el sistema.
- DT-017 (2026-10-07, reemplazada por DT-025): ~~dietas genéricas visibles para todos los nutricionistas~~. Fue una mala interpretación de la respuesta del desarrollador.

## Acceso a datos
- DT-018 (2026-10-07): Drizzle ORM (`drizzle-orm`, `drizzle-kit`) con el driver `postgres`, combinado con SQL directo según convenga (DT-002). Regla práctica: el ORM para CRUD y relaciones simples, donde da seguridad de tipos y menos código; SQL directo para agregaciones, estadísticas (RN-051, RN-052) y consultas donde la base procesa mejor que la aplicación. Ambos conviven en el mismo módulo y comparten la conexión. El SQL directo se escribe con la plantilla `sql` de Drizzle, que parametriza los valores (DT-003); nunca se concatena texto. Porqué Drizzle y no Prisma: deja escribir SQL propio sin pelear con el ORM. Las tablas viven en `src/modules/<dominio>/tables.ts` (las toma `drizzle.config.ts`) y las migraciones SQL se generan en `drizzle/`. Todavía no hay tablas ni conexión: se crean junto con el primer módulo que persista datos y con la base de Supabase (la conexión usa `DATABASE_URL`, secreta y solo de servidor).
- Nota (2026-10-07): `drizzle-kit` suma 4 avisos moderados de `npm audit` por un `esbuild` antiguo que arrastra. Es dependencia de desarrollo.

## Módulo usuarios
- DT-019 (2026-10-07): un usuario tiene `roles[]` (RN-002), no un rol único; corrige DT-014, que lo había interpretado mal. Porqué: la postulación aprobada solo agrega un rol y el Cliente se conserva; un usuario sin roles no tiene permisos, lo que permite bloquearlo sin borrarlo. Cada rol lleva su lista explícita de permisos, sin herencia (más datos repetidos, más flexibilidad): `src/modules/usuarios/roles.ts`. El nutricionista incluye los permisos del cliente (RN-020) y un test lo verifica. El admin tiene todos los permisos (RN-001).
- DT-020 (2026-10-07): la postulación a nutricionista o proveedor (`postulaciones.ts`) son funciones puras con resultado `{ ok, error }` y sin acceso a base de datos; reciben la fecha como parámetro para poder testearlas. Pendiente: no cambia roles; aprobar agrega el rol; rechazar no cambia nada y permite postularse de nuevo (supuesto, confirmado por el desarrollador). Deciden quienes tengan el permiso `application.decide` (admin y auditor, RN-043). Los campos del formulario de proveedor son un mínimo provisional (`businessName`).
- Se borró `src/tests/humo.test.ts`: ya existen tests reales (DT-012).
- DT-021 (2026-10-07): el usuario tiene un campo `adminNote` (nota interna del administrador, `usuarios/schema.ts`). Porqué: un usuario se bloquea dejándolo sin roles, sin borrarlo, y la nota deja constancia del motivo. Pendiente de definir: quién puede editarla y si el propio usuario puede verla.
- DT-022 (2026-10-07): se agrega el módulo `mascotas` (`pet`) a los módulos de dominio de DT-011, porque RN-010, RN-023 y VU-04 lo necesitan. La especie es texto libre hasta definir la lista cerrada de animales. Un alimento no puede ser a la vez de necesidad y alergénico o no permitido (coherencia de datos, no una regla de negocio nueva).
- DT-023 (2026-10-07): nadie decide su propia postulación, salvo el administrador (error `self_decision`). Cierra la pregunta sobre autoaprobación: evita que un auditor se apruebe a sí mismo como proveedor.
- DT-024 (2026-10-07): la especie de la mascota (y los tipos de mascota del producto) siguen siendo texto libre; la interfaz sugiere los valores que ya existen en la base (consulta de valores distintos) para evitar variantes como "Perro" y "perro". No hay lista cerrada. Pendiente al construir la interfaz.

## Dietas, versiones y asignaciones
- DT-025 (2026-10-07): cada nutricionista tiene sus propias dietas; no se comparten y se pueden asignar a varias mascotas. Se elimina la distinción genérica/específica (RN-022 queda absorbida). Reemplaza a DT-017. Porqué: dos mascotas muy parecidas pueden usar la misma dieta, y clonar cubre el caso de partir de una base. El nombre vive en la dieta y no se versiona.
- DT-026 (2026-10-07): versiones de dieta con congelamiento al asignar (RN-025 a RN-027). Una versión nunca asignada se edita y borra libremente; una vez asignada queda fija aunque la asignación termine, y los cambios crean una versión nueva con una alerta y la elección de qué mascotas la reciben. Porqué: no se acumulan versiones basura, y nunca se pierde lo que una mascota llegó a seguir. Las asignaciones terminadas se conservan con `endedAt`: sin ese historial no se sabría si una versión llegó a asignarse. Mover mascotas termina la asignación vieja y crea una nueva. Código en `src/modules/dietas/` (`versiones.ts`, `asignaciones.ts`).
- DT-027 (2026-10-07): permiso `diet.manage` (crear, editar, clonar y versionar) reemplaza a `diet.create_generic` y `diet.create_specific`; `diet.assign` queda aparte. Además del permiso se exige ser el dueño, así que un nutricionista sin roles (bloqueado) no puede actuar sobre sus dietas. Con dos casos reales (postulaciones y dietas) se extrajo `src/lib/result.ts` (tipo `Result`) y `Actor` en `usuarios/roles.ts`. Las funciones son puras: reciben ids y fecha por parámetro y devuelven `{ ok, ... }` o un código de error.

## Supabase
- DT-028 (2026-10-08): se usan las claves nuevas de Supabase: `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (pública, `sb_publishable_...`) y `SUPABASE_SECRET_KEY` (secreta, `sb_secret_...`) en lugar de `anon` y `service_role`, que Supabase deja como legado. Reemplaza los nombres de DT-013. `DATABASE_URL` usa el session pooler (puerto 5432) porque la conexión directa del plan gratuito es solo IPv6.
- DT-029 (2026-10-08): toda tabla del esquema `public` se crea con RLS (Row Level Security) activado. Porqué: la clave publishable es pública y viaja en el navegador; cualquiera puede usarla contra la API de datos de Supabase, así que una tabla sin RLS queda legible y escribible por cualquiera. Drizzle se conecta con `DATABASE_URL` como dueño de la base y no pasa por RLS: la autorización del lado servidor la siguen haciendo los módulos de dominio (`authorize`, `hasPermission`).
- Nota (2026-10-08): Node actualizado a 24 LTS. `vitest.config.mts` ya podría volver a `.ts`, pero no hace falta cambiarlo.

## Apariencia
- DT-030 (2026-10-08): módulo `apariencia` con 8 categorías de color por paleta (fondo, texto, primario, secundario, acento, error, éxito, advertencia; RN-070). Contraste mínimo 4,5:1 (WCAG AA, RN-072) para texto sobre fondo, texto sobre cada color y error/éxito/advertencia sobre el fondo. El texto que va sobre cada color no lo elige el admin: se calcula como el más legible entre su texto y su fondo. Paleta base en `paleta.ts` (RN-074); los valores pasan el contraste sin ajustes. Plan: `docs/superpowers/plans/2026-10-08-paleta-de-colores.md`.
- DT-031 (2026-10-08): Cache Components está activo (`cacheComponents: true`, ver corrección de DT-007). Para cachear datos se usa `"use cache"` con `cacheTag` y `cacheLife`, y se invalida con `updateTag` (en Server Actions) o `revalidateTag(tag, perfil)`; no `unstable_cache`. Ojo: el layout se pre-renderiza en el build, así que si la base falla durante `next build` la paleta base quedaría en el HTML estático; la Task 7 del plan tiene que resolverlo antes de implementarse.
- DT-032 (2026-10-08): modo claro/oscuro con `next-themes` (RN-073). Porqué: es lo que recomienda shadcn, sigue el sistema, guarda la elección en el navegador y evita el parpadeo con un script inline. Ese script se marca `text/plain` en el cliente (`scriptProps`) para que React 19 no avise en desarrollo, según la guía de Next `preventing-flash-before-hydration`.
- DT-033 (2026-10-08): la paleta se inyecta en `<head>` con selectores `html:root` y `html.dark`, más específicos que `:root` y `.dark` de `globals.css`, para que gane sin depender del orden en que Next carga los estilos. `globals.css` se genera desde la paleta base y un test verifica que coincidan. La página de inicio es provisoria (muestras de la paleta) hasta la landing VP-01.
- Límites conocidos (2026-10-08): `--muted-foreground` se valida solo contra el fondo (no contra `--muted`), y la variante `destructive` del botón pinta el error sobre un fondo rojo translúcido que no se valida. Revisar si aparecen problemas reales.

## Ingreso y usuarios
- DT-034 (2026-10-08): ingreso con Google vía Supabase Auth y `@supabase/ssr` (RN-003). Los clientes (`src/lib/supabase/`) se escribieron a mano siguiendo la documentación del paquete, en lugar del bloque de shadcn, para entender cada línea. `src/proxy.ts` (el middleware de Next 16) renueva la sesión en cada pedido y copia los encabezados anti-caché que entrega Supabase, para que un CDN no sirva la sesión de un usuario a otro. La sesión se valida con `getClaims()`, no leyendo la cookie. El proxy no decide permisos: cada Server Action y Route Handler llama a `getCurrentActor()` cerca de los datos. Después de ingresar se vuelve solo a rutas internas (`safeRedirectPath`), para que un enlace no pueda usar el ingreso para mandar a otro sitio.
- DT-035 (2026-10-08): tabla `users` con id igual al de `auth.users` (borrado en cascada), roles como `text[]` con restricción de valores válidos, RLS activado y sin políticas (DT-029). El primer ingreso la crea como Cliente con nombre y foto de Google; los siguientes no la tocan (RN-024), así un bloqueado sigue bloqueado. `onConflictDoNothing` cubre dos ingresos simultáneos. `db:migrate` carga `.env.local` con `node --env-file`, porque drizzle-kit no lo lee solo.
- DT-036 (2026-10-08): el menú del usuario en el encabezado llama a `connection()` antes de leer la sesión. Con Partial Prefetching, Next intenta preparar de antemano lo que depende de cookies, y Supabase usa `Date.now()` para ver si el token venció: Next lo rechaza ("unstable value Date.now()"). Se descartó `"use cache: private"` porque guardaría el usuario en el navegador y un bloqueo tardaría en notarse.
- DT-037 (2026-10-08): la paleta se lee con `"use cache"` + `cacheTag` y `cacheLife` condicional: `max` si la base respondió (se renueva solo al guardar, con `updateTag` en la Server Action) y `minutes` si falló o tardó más de 1,5 s. Porqué: con Cache Components el layout se pre-renderiza; así un fallo durante el build no deja la paleta base horneada, se corrige sola al minuto. La pantalla VA-08 lee sin caché y con 5 s de margen; si igual falla, no deja editar, para no pisar la paleta guardada con la base. Ningún valor que no sea hex llega al `<style>` (`sanitizePalette` dentro de `paletteCss`).
- DT-038 (2026-10-08): ajuste automático de contraste (RN-075): se mezcla el color con negro o blanco de a 1 % y se elige el menor cambio que cumple 4,5:1 en los pares de esa categoría. Porqué: conserva el tono elegido por el admin y es simple de entender y testear.
- DT-039 (2026-10-08): `safeRedirectPath` también rechaza rutas que la normalización deja como `//dominio` (ej. `/.//evil.com`), que un navegador interpreta como otro sitio.
- El primer admin (Sergio) se asignó a mano en la base el 2026-10-08. Los siguientes admins y auditores se asignan desde VA-10 (`/admin/usuarios`).

## Perfil, postulaciones y gestión de usuarios
- DT-040 (2026-10-08): tabla `applications` con los datos del formulario en `jsonb` (validados con `ApplicationDataSchema` al guardar y al leer) y un índice único parcial `(user_id, kind) where status = 'pending'`, que garantiza en la base una sola pendiente por tipo aunque lleguen dos envíos a la vez. Decidir corre en una transacción con `FOR UPDATE` sobre la postulación y el postulante, y usa las reglas puras de `postulaciones.ts`. Un usuario sin roles (bloqueado) no puede postularse. Después de cada acción se llama a `refresh()` (Next 16) para que la página y el encabezado muestren el cambio.
- DT-041 (2026-10-08): en VA-10 el admin edita los roles con casillas y la nota interna. Un admin no puede quitarse su propio rol de admin, para no dejar el sistema sin quien lo administre. La nota no la ve el usuario.
- DT-042 (2026-10-08): si el alta del usuario falla al ingresar (base caída o email ya usado por otra cuenta), se cierra la sesión y se vuelve con `?ingreso=error`, que muestra un aviso. `onConflictDoNothing` apunta solo al id para que un conflicto de email no pase en silencio.
